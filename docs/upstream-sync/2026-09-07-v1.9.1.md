## 本次留下的技术经验

1. **命令接受与数据完整分开判断。** SELECT 返回 61xx 表示已接受；后续取响应体失败不应反向否定 SELECT。
   但 READ 缺数据、AKA 失败不能被包装成成功。PIN、IKE、SIP 共用选择器和交换规则，避免三条路径漂移。
2. **缓存必须有可验证的适用范围。** 无 PIN 卡的 eSIM 加速只复用同次操作中有时效、reader 绑定及当前卡身份
   依据的结果；锁内再核对，其他启动路径执行完整预检。不能用一个布尔“已检查”覆盖所有启动。
3. **补片是一条消息的更新。** 正文与补片状态在同一事务提交；WebSocket 使用原 sms 事件的 updated 标志，
   刷新原记录、重做相关解析，但不重复新短信提示和推送。
4. **模块数量不能替代集合验证。** 检查完整名称、缺失、多余、重复及规范化集合 SHA-256。清单进入
   base fingerprint；只计算受 Git 管理的输入。旧 336 模块代按旧源码验证，不能套新清单阻止回滚。
5. **构建身份绑定准确提交。** 无缓存验证完成后，受管 prepare 仍按实际产物写 manifest。镜像重新导出时
   ID 可能不同，核对当次 manifest/实际镜像及源码、版本、指纹，不能拿另一次构建的 ID 机械比较。
6. **固定行为不等于固定版本号。** 后续升到 `.2` 时，现有版本测试仍写死 `.1` 而失败；应同步维护版本契约，
   不能删掉验证。UI 的三套拨号盘也在后续收敛为共享组件，说明共享状态之外还要共享呈现规则。

## 正式更新发现的 Git 对象问题

开发仓库完整，正式仓库却在 fetch 时出现 `pack has 101 unresolved deltas`。只读检查发现缺少
946 个历史 blob，残留两个 `.promisor` 标记，但没有相应 partial/promisor 配置。不能只检查开发仓库
完整性，也不能仅凭 clone 配置未设置 promisor 就认定对象齐全；具体遗留状态何时引入未追溯确认。

先在仓库外 root-only 的 Git 元数据副本中复现，再验证禁用“已有哪些对象”的协商后完整获取可以补齐。
确认副本 `git fsck --full --no-dangling` 通过后，仅对那次受管更新执行：

```bash
sudo env GIT_CONFIG_COUNT=1 \
  GIT_CONFIG_KEY_0=fetch.negotiationAlgorithm \
  GIT_CONFIG_VALUE_0=noop \
  /usr/local/sbin/mddctl update --yes
```

这是一项针对已诊断现场的恢复经验，不是日常更新命令，也不是所有损坏仓库的通用修复。
管理器仍检查当前代、远端、快进关系、构建、备份和激活；未手工改正式分支或持久 Git 配置。
完成后正式仓库全对象检查通过，缺失数归零。[Git 对该选项的说明](https://git-scm.com/docs/git-config#Documentation/git-config.txt-fetchnegotiationAlgorithm)

期间还有独立的 GitHub TLS 握手失败，均在停服前退出。先确认失败阶段和服务状态，再决定受管重试，
不要把网络重试、对象修复与事务回滚混为一谈，也不要关闭 TLS 校验。

## 证据保存经验

早期 /tmp 中的构建日志和浏览器截图在快照前关机/重启后消失，后续记录已明确说明原件不再可用。
新的脱敏总结和虚构预览放到持久文档目录；原始数据、Git 元数据副本和完整日志保存在仓库外 root-only 位置。
快照回退仍会回退 VM 内文件，故跨快照需要的证据应先另存到宿主机。

本次管理器会轮换 pre-update 归档。执行后续 `.2` 更新前，先把更早的更新前归档和摘要另存到受限目录并
核对摘要，避免把轮换误写成“所有原路径永久保留”。未来应按当前管理器的实际保留策略记录恢复材料的位置。
